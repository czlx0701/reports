ParentMap 本周末活动任务 · 模型评测总报告

任务题面（v5，原文）： 
从 https://www.parentmap.com/calendar/ 去找本周末的活动。

范围：本周末（周六、周日两天）的全部活动。

筛选条件：
- 只看 Eastside（东区）的活动；
- 年龄只算 preschool 和 elementary 这两档，主要是给 6 岁的孩子玩；
- 从 Bellevue 出发，开车单程超过 1 小时的扔掉。

从符合条件的所有活动里挑出你**最推荐的 10 个**（符合条件的不到 10 个就如实写几个，不要凑数）。
每条写清楚：是干什么的、有什么亮点、有什么注意事项。按推荐度从高到低排。

写进 <OUT 路径>
限定只用浏览器通道（Steel REST / CDP / Playwright / 内置 browser），搜索由插件层硬拦。真值：周末全量 225 条 → Eastside ∩ preschool/elementary = 56 场次（38 个去重活动）。
判分：盲评（22 个独立评分员，一评一员）；内容 90 = 事实 30 + 决策 25 + 主动性 20 + 出处诚实 15；效率 10 = 时间分（≤500s=5…>1000s=1）+ 体量分（≥13KB=5…<7KB=1），客观数据不进盲评。
样本：云端 3 臂 ×3 = 9 条；本地 4 模型 9 条；本地 baseline 组合矩阵 4 配置共 8 条。n≤5，只报分差与失效模式，不做排名。

一、头条结论

1. 加"精简十条"是本次唯一的显著增益：内容分 58.4 → 77.5，耗时 1175s → 300s。 同一个本地模型（3.6-35B-A3B-4bit）、同一题面，只换提示词配置：裸 59.8 ｜ 只 pre-flight 58.4 ｜ + 十条原版 69.1 ｜ + 精简十条 77.5。 精简版两条样本内容分 78 / 77（几乎一致），且是全部本地 run 里最快的（240s / 360s）。可信度限制：每格 n=2、且不同配置跑在 oMLX 不同负载窗口（见第六节），只能当强方向性信号。
2. 只 pre-flight vs 裸 = 无差异（58.4 vs 59.8，两条臂各自样本内离散度都很大：裸 75/44.5、只 pre-flight 73/58.5/43.8）。光灌 pre-flight 不改变这题的成绩分布；真正起作用的是那十条里的"交付物先行 + 逐候选查当日 + 未取得要带证据"。而原版十条只拿到 69.1，精简掉"搜索通道菜单 / 与 pre-flight 重复的条款"后升到 77.5。
3. 本地最强模型（3.8-27B）能力已追平云端：内容 84.5 vs 云端同臂 85.7（差 1.2，n=2 vs 3）。总分 88.5 vs 95.0 的差距全部来自效率（1210s vs 484s、9.1KB vs 17.9KB）。其余本地模型断层：3.6-OptiQ 59.8 ｜ 基线 58.4 ｜ AgentWorld 47.7；云端三臂集中在 83–86。
4. pre-flight 原版 vs 不灌（云端）= 无差异（95.0 vs 94.3，差 0.7）。方向性细节：原版交付更薄却同分（17.9KB vs 20.2KB）。本地"不灌"未取得（主臂全部灌了 pre-flight；矩阵里的"裸"臂等价于不灌，见结论 2）。
5. 我改的"瘦身 pre-flight(B)"在云端是负资产，未落盘。云端 91.0 vs 原版 95.0，慢 60%（772s vs 484s）。机制：我在 4 处给 Steel/CDP 最贵路径做了广告 + 把"可复制命令/环境硬事实"换成"条件式通道菜单"（第八节）。注意这与结论 1 不矛盾：坏的是那个 pre-flight 改写，好的是精简后的十条规则 —— 后者删掉通道菜单、保留可执行纪律。
6. 事故必须拆两类算，不能混成"崩溃率"。本地 64 次尝试：有效交付 27 ｜ harness 看门狗误杀 11 次（是我判活方式的 bug：stdout 整轮才落盘，见第六节） ｜ 模型侧失败 14 次（其中畸形 tool call 7 次）｜ 误杀 1 次。云端 3 次尝试 0 事故。

测量可信度警告（重要，两条）
(1) stdout 是整轮才落盘的，"输出文件没长"≠卡死。实测：一条 run 的 run.out.txt 长时间停在 355B，而同一 run 的会话库（state.db.messages）里工具调用与消息持续写入、oMLX 确在生成。据此重判：本报告早期把「输出静默」当卡死是错的，约十余条 run 是被我给评测 harness 加的看门狗误杀的（结果未知，既不算模型失败也不算服务故障），其中若干是健康 run。正确判活方式 = 查会话库最新消息时间戳，已改进 harness。
(2) 效率分含机器抖动，只看方向。同配置有效 run 的耗时跨度从 240s / 360s / 420s 一直到 1451s / 2103s；同一时间窗内 oMLX 每轮生成要 3–4 分钟（会话消息间隔 169s→226s→104s），跨窗口不可比。内容分由盲评给出、不依赖耗时。

八、为什么"瘦身 pre-flight(B)"在云端更慢更差（机制已查清）

  • M1｜我在 4 处给最贵的取数路径做了广告：Step 1 技能路由、Step 2 正文、Step 10 验证、Pitfalls 都新增了 Steel/CDP（原版 0 处提及）。实测 playwright 在 B 臂一条 run 里出现 29 次，其余 8 条 run 全为 0；那条走 Playwright-over-Steel 逐页渲染，77 次调用 / 1123s（对照臂 41–48 次 / 383–562s）。
  • M2｜"硬事实 + 可复制命令"被换成"条件式通道菜单"：原版 Step 2 是"唯一通道 + 两行可复制命令 + 环境硬事实（web toolset 已禁用）"；B 版改为"搜索只是线索、被拦就改走浏览器"。实测搜索两臂都没真用过（search_blocked=0）→ 该改动净值纯负，只多出决策负担。
  • M3｜删掉 3 处可复制命令 + 新增"别假设列表默认视图就是当前的"：取数从一次窗口化 REST 查询退化为逐日渲染整页（B 臂一条渲染 9 个 450KB 页面，到第 20 次 terminal 调用才补 REST）。
  • 量化：>60s 长尾调用 B 12 次/404s（占其壁钟 53%）vs 对照 3 次/102s；"terminal 里批量 HTTP"B 337s vs 89s —— 差额的 86% 在这一项。反直觉：B 臂 browser_exec 反而更少（2.7 vs 4.7）。
  • 教训：skill 里"删命令 / 加可选通道"本身就是行为干预，必须当变量测，不能当瘦身；规则里出现"某条通道"的名字，模型就更容易走那条最贵的路。
